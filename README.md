# SPIKE Prime PID + Pure Pursuit

Автономная навигация для **LEGO SPIKE Prime** в **SPIKE App 3.x**.

Робот едет по ломаной из точек `[(x, y), ...]`: энкодеры моторов считают путь, **угол курса Theta берётся только с гироскопа хаба**, PID держит курс на точку Pure Pursuit.

Файл проекта один: [`main.py`](main.py). Его целиком вставляют в Python-проект SPIKE App. Отдельные модули App 3.x на хаб не кладёт.

## 1. Что это и для кого

Это не Pybricks и не Word Blocks. Стек строго такой:

| Слой | Что используем |
| --- | --- |
| Приложение | SPIKE App **3.x**, язык **Python** |
| Цикл | `import runloop` → `async def main()` → `runloop.run(main())` |
| Моторы | `import motor` + `from hub import port` |
| Гироскоп | `from hub import motion_sensor` → `tilt_angles()` |
| Математика | `import math` |

Задачи, которые решает код на соревновании FLL:

- проехать заданную ломаную по ковру, не рисуя движение «на глаз» блоками `move_for_degrees`;
- держать курс по IMU, а не по разности колёс (колёса на ковре FLL проскальзывают);
- плавно проходить углы траектории (Pure Pursuit), а не стопориться в каждой вершине.

Ограничение MicroPython на хабе: нет файлов, нет `numpy`, нет потоков. Поэтому всё — один файл, цикл 10 мс, float-арифметика.

## 2. Как читать и править код в SPIKE App 3.x

### 2.1. Карта файла: три зоны, которые трогают, и одна — которую нет

Откройте `main.py`. Файл читается сверху вниз как учебник.

```
┌─────────────────────────────────────────────────────────────┐
│  import math / motor / runloop / hub                        │  не трогать
├─────────────────────────────────────────────────────────────┤
│  НАСТРОЙКИ РОБОТА                                           │  ★ правите здесь
│    WHEEL_DIAMETER, WHEELBASE                                │
│    LEFT_MOTOR_PORT, RIGHT_MOTOR_PORT, *_SIGN                │
│    YAW_FACE, GYRO_SIGN                                      │
│    PID_KP, PID_KI, PID_KD                                   │
│    BASE_SPEED, LOOKAHEAD_MM, PATH                           │
├─────────────────────────────────────────────────────────────┤
│  утилиты clamp, wrap_deg                                    │  не трогать
│  class Odometry                                             │  не трогать
│  class PID                                                  │  не трогать
│  class PathFollower                                         │  не трогать
│  apply_tank / stop_drive / cruise_speed                     │  не трогать
├─────────────────────────────────────────────────────────────┤
│  async def main():   — главный цикл 10 мс                   │  редко
│  runloop.run(main()) — точка входа                          │  не удалять
└─────────────────────────────────────────────────────────────┘
```

**Правило FLL-команды:** на турнире меняют только блок настроек и массив `PATH`. Алгоритм уже собран.

### 2.2. Где настройки

Сразу после импортов, комментарий:

```text
# НАСТРОЙКИ РОБОТА — РЕДАКТИРУЙТЕ ЭТОТ БЛОК
```

Каждая константа подписана. Меняйте числа, не переименовывайте переменные: на них ссылается движок.

Минимальный набор, который нужно выставить под СВОЮ базу, прежде чем ехать:

1. `WHEEL_DIAMETER` — мм, реальный диаметр шины.
2. `WHEELBASE` — мм, колея между серединами ведущих шин.
3. `LEFT_MOTOR_PORT` / `RIGHT_MOTOR_PORT` — ведущие **C** и **E**.
4. `LEFT_MOTOR_SIGN` / `RIGHT_MOTOR_SIGN` — направление «вперёд».
5. Порты датчиков и навесов: **A+D** цвет, **B+F** механизмы (константы уже в настройках).
6. `PATH` — ваши точки в мм.

PID и lookahead трогают только после того, как робот хотя бы едет вперёд и поворачивает в нужную сторону.

### 2.3. Где точки траектории

Массив `PATH` в том же блоке настроек:

```python
PATH = [
    (0.0, 0.0),      # старт. Робот стоит здесь, нос по +X
    (400.0, 0.0),    # 400 мм вперёд
    (400.0, 300.0),  # 300 мм влево
    (750.0, 300.0),
    (750.0, 0.0),
]
```

Система координат (жёстко зашита в одометрию):

```
        +Y (влево от робота на старте)
        ↑
        │
        ●────→ +X (нос робота в момент reset)
      (0,0)
```

Единицы — **миллиметры**. Координаты поля FLL удобно снимать линейкой / по клеткам коврика (клетка 30 см = 300 мм).

Не ставьте две одинаковые точки подряд. Не делайте сегмент короче `WAYPOINT_RADIUS_MM` без нужды: точка будет «проглочена» сразу.

### 2.4. Где главный цикл

Внизу файла:

```python
async def main():
    ...
    while True:
        odom.update()
        ...
        await runloop.sleep_ms(LOOP_MS)

runloop.run(main())
```

Это не «обычный» `while True` из учебника Python. На SPIKE App 3.x моторы и датчики живут в кооперативном runloop. Без `await runloop.sleep_ms(...)` хаб не отдаст управление, гироскоп и моторы «замерзнут», программа зависнет.

`runloop.run(main())` — обязательная последняя строка. Если её стереть, Play ничего не запустит.

Внутри кадра цикла (каждые 10 мс) происходит одно и то же:

1. `odom.update()` — новые x, y, theta.
2. `follower.update(x, y)` — новая точка преследования; `False` = финиш.
3. Ошибка курса = желаемый heading − гироскоп.
4. `pid.compute(...)` — угловая скорость.
5. `apply_tank(...)` — скорости левого и правого моторов.
6. `await runloop.sleep_ms(10)` — пауза кадра.

### 2.5. Как вставлять код в редактор App

1. В SPIKE App откройте Python-проект (иконка `<>`, не цветные блоки).
2. Сотрите шаблон `async def main()` / `runloop.run`, который App подставляет сам.
3. Вставьте **весь** `main.py` от первого `import` до `runloop.run(main())`.
4. Не оставляйте второй `runloop.run` — будет двойной запуск.
5. Сохраните проект именем вроде `PurePursuit`.

Редактор App не умеет «файл рядом». Комментарии на русском можно оставить: интерпретатор их игнорирует.

Отступы — только пробелы, 4 пробела. Не смешивайте с Tab: App иногда ломает выравнивание при копировании из браузера. Если после вставки «поехал» весь класс, выделите код и проверьте, что `class` и `def` на своих колонках.

## 3. Пошаговый запуск: от нового файла до Play

### Шаг 1. Железо

- Хаб SPIKE Prime, прошивка актуальная для App 3.x.
- Два мотора на ведущих колёсах (Large или Medium — оба работают; скорость `BASE_SPEED` подберите).
- Два гладких колеса **без резиновых шин** (голый диск / скользкая втулка) как опоры. Они должны свободно проскальзывать вбок.
- Хаб желательно матрицей вверх (`YAW_FACE = motion_sensor.TOP`). Если матрица смотрит в другую сторону — смените константу, иначе yaw будет врать.

Поставьте робота на ровный стол. Не держите его в руках при старте: `reset_yaw(0)` запомнит «ноль» криво.

### Шаг 2. Кабели

Карта портов **этой базы** (зашита в `main.py`):

| Роль | Порт |
| --- | --- |
| Левый ведущий | `port.C` |
| Правый ведущий | `port.E` |
| Цветовой датчик | `port.A` |
| Цветовой датчик | `port.D` |
| Навесной мотор | `port.B` |
| Навесной мотор | `port.F` |

```python
LEFT_MOTOR_PORT = port.C
RIGHT_MOTOR_PORT = port.E
COLOR_SENSOR_A = port.A
COLOR_SENSOR_D = port.D
ATTACHMENT_MOTOR_B = port.B
ATTACHMENT_MOTOR_F = port.F
```

Навигация крутит только C и E через `motor.run`. B и F на старте останавливаются, чтобы механизмы не поехали вместе с базой. A и D зарезервированы под цвет (линия / развилка) — в цикл Pure Pursuit пока не входят.

Допустимые порты: `port.A` … `port.F`. Не путайте с `motor_pair.PAIR_1` — этот проект motopair не использует.

Если робот крутится на месте сразу после Play — перепутаны левый/правый: поменяйте C и E в `LEFT_MOTOR_PORT` / `RIGHT_MOTOR_PORT`.

### Шаг 3. Создать Python-проект в SPIKE App 3.x

1. Запустите SPIKE App 3.
2. Подключите хаб по Bluetooth или USB.
3. **New project** → **Python** (не Word Blocks).
4. Имя проекта: любое.
5. Полностью замените содержимое редактора на `main.py`.

### Шаг 4. Первая проверка знаков моторов (обязательно)

Временно поставьте в `PATH` две точки:

```python
PATH = [
    (0.0, 0.0),
    (300.0, 0.0),
]
```

Нажмите **Play**. Робот должен поехать **вперёд** примерно на 30 см и остановиться.

| Что произошло | Что менять |
| --- | --- |
| Поехал назад | Смените оба знака: `LEFT_MOTOR_SIGN` и `RIGHT_MOTOR_SIGN` на противоположные |
| Крутится на месте влево | Инвертируйте только `RIGHT_MOTOR_SIGN` |
| Крутится на месте вправо | Инвертируйте только `LEFT_MOTOR_SIGN` |
| Поехал вперёд, но дугой | Это уже PID / гироскоп, не знаки. Сначала добейтесь прямой |

Знак мотора = «положительная скорость крутит это колесо вперёд». У базы, где моторы стоят осями наружу, почти всегда `LEFT_MOTOR_SIGN = -1`, `RIGHT_MOTOR_SIGN = 1`.

### Шаг 5. Проверка гироскопа

Оставьте тот же короткий `PATH` на 300 мм вперёд. Робот должен ехать **прямо**, а не дугой.

Если уходит зеркально (коррекция увеличивает дугу):

```python
GYRO_SIGN = -1
```

Если дуга слабая — это калибровка `WHEEL_DIAMETER` / PID, см. раздел 4.

Перед стартом **не крутите** хаб. В `main()` есть пауза 400 мс и повторный `reset()`: робот должен стоять.

### Шаг 6. Боковой заезд

```python
PATH = [
    (0.0, 0.0),
    (400.0, 0.0),
    (400.0, 300.0),
]
```

Ожидание: вперёд 40 см, плавная дуга, затем вдоль +Y (влево). Если поехал вправо — снова `GYRO_SIGN` или перепутаны «лево/право» порты.

### Шаг 7. Боевая траектория

Верните полный `PATH` под миссии. Ставьте робота на старт **носом вдоль +X**, центр оси ведущих колёс над (0, 0) вашего листа/ковра.

Нажмите **Play** один раз. Повторный Play без перестановки сдвинет систему координат: `reset()` считает текущее место нулём.

### Шаг 8. Остановка

Программа сама вызывает `stop_drive()` на финише. Аварийно — кнопка Stop в App или кнопка на хабе.

## 4. Калибровка и настройка

### 4.1. Как правильно измерить `WHEEL_DIAMETER`

Не верьте цифре на детали вслепую. Резина сжимается, обод бывает 56 мм «по каталогу» и 54–55 мм «по полу».

**Метод линейки (быстрый)**

1. Снимите колесо.
2. Штангенциркулем измерьте диаметр по наружной резине в двух местах, усредните.
3. Запишите в `WHEEL_DIAMETER` в миллиметрах, например `55.4`.

**Метод выбега (точный, рекомендуемый для FLL)**

1. Поставьте `PATH = [(0, 0), (1000.0, 0.0)]`.
2. Выставьте PID так, чтобы робот ехал максимально прямо (`GYRO_SIGN` уже верный).
3. Отметьте старт и финиш на полу.
4. Запустите. Измерьте фактический пробег линейкой: `S_факт`.
5. Пересчитайте:

```text
WHEEL_DIAMETER_новый = WHEEL_DIAMETER_старый * (S_факт / 1000)
```

Пример: стояло 56.0, проехал 972 мм → `56.0 * 0.972 = 54.43`.

Повторите 3 раза, усредните. Калибруйте на том же покрытии, что и поле: на столе и на коврике FLL диаметр «эффективный» разный из‑за смятия резины.

Одометрия использует

```text
путь_колеса_мм = (обороты_в_градусах / 360) * π * WHEEL_DIAMETER
```

Ошибка диаметра на 2% даёт 2 см промаха на каждом метре. На миссии «через всё поле» это уже другая клетка.

`WHEELBASE` измерьте линейкой между **центрами протекторов** ведущих колёс, не между внешними краями. Нужен для перевода выхода PID в разность скоростей моторов. На Theta не влияет (Theta с гироскопа).

### 4.2. Как указывать порты моторов

В SPIKE App 3.x порты — это константы модуля `hub.port`, не строки и не числа, которые вы придумали:

```python
from hub import port

LEFT_MOTOR_PORT = port.C    # да, ведущий левый на этой базе
# LEFT_MOTOR_PORT = "C"     # нет, упадёт
# LEFT_MOTOR_PORT = 0       # нет
```

Допустимо: `port.A`, `port.B`, `port.C`, `port.D`, `port.E`, `port.F`.

На этой машине:

- база едет с **C** (лево) и **E** (право);
- цвет — **A** и **D**;
- механизмы — **B** и **F**.

Левый = тот, что слева, если смотреть **из-за робота по ходу движения** (как водитель). Правый — зеркально. Если C оказался физически справа — поменяйте константы местами.

После смены порта всегда заново проверяйте `*_SIGN` (шаг 4 запуска). Мотор, переставленный с другой стороны, часто оказывается «вперёд = минус».

Энкодер читается так:

```python
motor.relative_position(LEFT_MOTOR_PORT)
motor.reset_relative_position(LEFT_MOTOR_PORT, 0)
```

Знак в одометрии:

```text
deg_для_математики = relative_position(порт) * MOTOR_SIGN
```

Положительный `deg_для_математики` = это колесо едет вперёд.

### 4.3. Пошаговый подбор PID: Kp, Ki, Kd

Регулятор стоит **на ошибке курса** (градусы), выход — желаемая угловая скорость кузова. Это не PID по позиции X/Y.

```text
e = wrap( heading_желаемый − heading_гироскопа )     # (−180, 180]
u = Kp·e + Ki·∫e dt + Kd·de/dt
```

Anti-Windup уже в классе `PID`:

- интеграл не копится, если выход насыщен и ошибка того же знака;
- `|интеграл|` ограничен `PID_I_LIMIT`.

Из‑за этого можно держать небольшой `Ki` без «взрыва» после долгого упора в лимит моторов.

**Готовьте полигон.** Прямая 80–100 см + один поворот на 90°. Меняйте **один** коэффициент за заезд. Записывайте тройку (Kp, Ki, Kd) в таблицу.

#### Этап A — только пропорциональный член

```python
PID_KP = 1.0
PID_KI = 0.0
PID_KD = 0.0
```

Запускайте прямую.

| Поведение | Действие |
| --- | --- |
| Едет, но медленно «стекает» с курса, дуга большая | Увеличьте `PID_KP` шагом 0.5 |
| Осцилляции: нос виляет влево-вправо | Уменьшите `PID_KP` на 20–30% — это ваш потолок |
| Стоит и дёргается на месте | `Kp` слишком большой **или** `GYRO_SIGN` неверный |

Рабочий FLL-диапазон для `BASE_SPEED ≈ 350…450`: **Kp = 2.0 … 4.5**. Запомните значение, при котором начинается лёгкий дрожащий виляние, и возьмите **60–70%** от него. Это стартовый Kp.

Почему не сразу большой Kp: на ковре есть люфт и задержка 10 мс. Слишком злой P превращает робота в маятник.

#### Этап B — дифференциальный член (демпфер)

Оставьте найденный Kp.

```python
PID_KD = 0.2
```

| Поведение | Действие |
| --- | --- |
| Виляние после поворота осталось | Увеличьте Kd шагом 0.05…0.1 |
| Робот «ватный», поздно начинает поворот, срезает угол | Kd слишком большой — уменьшите |
| Шипение / дрожь на прямой при живом гироскопе | Kd ловит шум IMU — уменьшите или не растите |

Kd гасит скорость изменения ошибки. Он нужен, чтобы после 90° робот не пролетел курс и не качнулся обратно.

Практичный диапазон: **Kd = 0.2 … 0.6** при цикле 10 мс.

#### Этап C — интегральный член (убирает остаточную дугу)

Многие FLL-базы едут приемлемо при `Ki = 0`. Включайте I только если на длинной прямой остаётся **постоянный** увод 2–5°, который P не добивает (механическая асимметрия, разная резина).

```python
PID_KI = 0.02
```

Шаг 0.02. Смотрите длинную прямую 1.5–2 м.

| Поведение | Действие |
| --- | --- |
| Увод на прямой уменьшился, повороты те же | Хорошо, можно ещё чуть добавить |
| На повороте робот «перекручивает» и долго выправляется | Ki велик — уменьшите; Anti-Windup помогает, но не творит чудеса |
| После стопора у стены / у препятствия робот резко срывается в сторону | Интеграл накопил ошибку. Уменьшите Ki и/или `PID_I_LIMIT` |

Практичный диапазон: **Ki = 0.00 … 0.08**. Начните с нуля.

`PID_I_LIMIT = 80` — разумный потолок. Если после столкновения с моделью робот уезжает «пьяным», снизьте до 40.

`PID_OUTPUT_LIMIT` режьте, если на поворотах колесо срывается в писк: меньше лимит → спокойнее разворот.

#### Этап D — скорость и lookahead вместе с PID

PID настроен на конкретной `BASE_SPEED`. Подняли скорость с 380 до 600 — Kp часто надо слегка уменьшить, lookahead — увеличить.

Грубое правило:

```text
LOOKAHEAD_MM ≈ (1.0 … 2.0) × WHEELBASE
```

Для колеи 120 мм начните со 160 мм.

| Симптом | Правка |
| --- | --- |
| Срезает углы, не доезжает до вершины | Уменьшите `LOOKAHEAD_MM` |
| Дёргается на каждой вершине, «кусает» точку | Увеличьте `LOOKAHEAD_MM` |
| Промахивает финиш | Увеличьте `SLOWDOWN_MM` или уменьшите `GOAL_TOLERANCE_MM` |
| Останавливается, не доехав | Увеличьте `GOAL_TOLERANCE_MM` ( slack на ковре) |

#### Чего не делать

- Не крутите Kp, Ki и Kd одновременно.
- Не калибруйте PID, пока знаки моторов и гироскопа неверны — вы «настроите» компенсацию бага.
- Не ставьте Ki большим «чтобы лучше держал». На FLL интеграл — тонкая шпаклёвка, не основной руль.
- Не сравнивайте свои коэффициенты с чужой командой 1-в-1: другая колея, другие колёса, другой `dt`.

### 4.4. Как задавать свои координаты и траектории

Точка — кортеж `(x_мм, y_мм)`. Список — ломаная. Робот не обязан посещать вершины буквально: Pure Pursuit целится в точку на расстоянии `LOOKAHEAD_MM` вдоль пути. Вершина «засчитывается», когда робот входит в `WAYPOINT_RADIUS_MM`.

**Прямая туда-обратно**

```python
PATH = [
    (0.0, 0.0),
    (600.0, 0.0),
    (0.0, 0.0),
]
```

На обратном пути робот развернётся сам: желаемый heading станет ~180°.

**Квадрат 40×40 см против часовой**

```python
PATH = [
    (0.0, 0.0),
    (400.0, 0.0),
    (400.0, 400.0),
    (0.0, 400.0),
    (0.0, 0.0),
]
```

**Объезд модели справа (Y отрицательный = вправо от стартового носа)**

```python
PATH = [
    (0.0, 0.0),
    (250.0, 0.0),
    (250.0, -180.0),
    (700.0, -180.0),
]
```

**Как снять точки с поля**

1. Положите робота на старт. Нос = +X.
2. Для каждой ключевой позы измерьте смещение центра оси ведущих колёс: вперёд (X) и влево (Y). Вправо — отрицательный Y.
3. Вставляйте точки чаще там, где нужен точный коридор (между моделями): шаг 80–150 мм.
4. На открытом участке шаг 200–400 мм, иначе ломаная излишне ломаная.

**Частые ошибки в PATH**

| Ошибка | Результат |
| --- | --- |
| Забыли (0, 0) первой точкой | Первый сегмент тянет робота в бок сразу со старта |
| Смешали см и мм: написали `(40, 0)` вместо `(400, 0)` | Робот сразу «на финише» |
| Точка позади робота без разворота в пути | Кратчайший курс может быть разворотом — это нормально, но заложите место |
| Две точки ближе 2–3 см | Сегмент вырожден, lookahead прыгает |

Менять траекторию между заездами — это правка `PATH` и Play. Пересобирать классы не нужно.

## 5. Кинематика базы: 2 ведущих + 2 гладких

### 5.1. Схема

```
          направление +X (нос)
                 ↑
                 │
     ┌───────────┴───────────┐
     │                       │
   ◯ резиновое          резиновое ◯     ← ведущие, моторы C / E
   (лево)                  (право)
     │     хаб, цвет A+D     │
     │   навесы B+F, гиро     │
     │                       │
   ○ гладкое            гладкое ○       ← БЕЗ резины, скользят
     └───────────────────────┘

           колея WHEELBASE
     |←─────────────────────→|
```

Ведущие колёса стоят на одной оси (или почти). Гладкие — сзади или по углам рамы. Их задача — **держать высоту и не мешать повороту**.

### 5.2. Почему гладкие колёса без резины

Дифференциальный привод **неголономен**: робот не умеет ехать боком. Поворот вокруг мгновенного центра вращения (ICR) требует, чтобы точки контакта скользили или катились по дуге.

Если все четыре колеса в резине:

- при развороте диагональные опоры **скребут** ковёр;
- энкодеры ведущих колёс показывают не тот путь, который центр реально прошёл;
- PID борется с механикой, моторы греются, курс плывёт.

Голый диск / скользкое колесо:

- сила трения вбок маленькая;
- база крутится вокруг вертикали почти как идеальный дифф. привод;
- гироскоп видит чистый yaw без дёрганья рамы.

Не смазывайте опоры маслом на турнире (ковёр FLL, судьи). Достаточно снять резину со стандартного колеса или поставить ролик без шины.

Опоры ставьте так, чтобы **не несли большую долю веса**. Вес — на ведущих: иначе ведущие проскальзывают, одометрия по пути врёт (Theta при этом всё ещё с гироскопа, но X/Y поедут).

### 5.3. Модель движения

Пусть `s_L`, `s_R` — путь левого и правого ведущего колеса.

Классический дифф. привод:

```text
Δs = (Δs_L + Δs_R) / 2           линейное перемещение центра оси
Δθ = (Δs_R − Δs_L) / WHEELBASE   изменение курса  ← в этом проекте НЕ используем
```

Здесь **вторая строка выкинута**. Вместо неё:

```text
θ = gyro_yaw = tilt_angles()[0] * 0.1° * GYRO_SIGN
x += Δs * cos(θ)
y += Δs * sin(θ)
```

`Δs` по-прежнему из моторов. Даже если одно колесо пробуксовало, курс не «ломается» на величину пробуксовки. Ломается только оценка пройденного пути — поэтому диаметр колеса и равномерный прижим так важны.

Мгновенный центр вращения: если `v_L = v_R` — ICR в бесконечности, езда прямо. Если `v_L = −v_R` — ICR по центру оси, разворот на месте. Гладкие колёса позволяют ICR гулять без скрежета.

### 5.4. Смешивание скоростей (tank)

PID выдаёт `ω` (град/с кузова). Перевод в моторы:

```text
δ = ω * (WHEELBASE / WHEEL_DIAMETER)
v_L = v_база − δ
v_R = v_база + δ
```

Дальше масштабирование, если кто-то упёрся в `MAX_MOTOR_SPEED`, и умножение на `MOTOR_SIGN`.

Плюс `ω` при движении вперёд ускоряет **правое** колесо → поворот против часовой → +Y. Это согласовано с гироскопом LEGO (плюс = CCW).

### 5.5. Как ставить хаб

Идеал: матрица светодиодов вверх, USB назад или вперёд — как удобно, но **плоско**. Тогда

```python
YAW_FACE = motion_sensor.TOP
```

Если хаб лежит «на спине» или матрицей вперёд, вызовите соответствующую грань: `FRONT`, `BACK`, `LEFT`, `RIGHT`, `BOTTOM`. Иначе `tilt_angles()` будет мешать yaw с roll, и на кочке полетит курс.

Не ставьте хаб на вибромоторы наклеек. Люфт хаба = шум Kd.

## 6. Как устроен движок

### 6.1. Odometry

- Читает `motor.relative_position` обоих ведущих.
- Переводит градусы энкодера в мм через `πD`.
- Берёт yaw из `motion_sensor.tilt_angles()[0]` (дециградусы → градусы).
- Интегрирует `x, y` в мире старта.

Вызов `reset()`: `set_yaw_face`, `reset_yaw(0)`, обнуление энкодеров и позы. В `main()` reset делается дважды с паузой 400 мс — IMU после включения иногда отдаёт мусор в первых сотнях миллисекунд.

### 6.2. PID

Вход — ошибка курса, уже обёрнутая в (−180, 180]. Без обёртки переход 179° → −179° выглядел бы как скачок 358° и робот крутанулся бы не в ту сторону.

Anti-Windup:

1. **Conditional integration.** Если `|u| ≥ лимита` и ошибка того же знака, что и u, интеграл заморожен. Смысл: моторы уже крутят на максимум, копить «ещё больше» бесполезно и вредно.
2. **Clamp.** `|I| ≤ PID_I_LIMIT`.

D-член считается по `(e − e_prev) / dt`. Первый кадр D = 0, чтобы не ударить стартовым скачком.

### 6.3. PathFollower (Pure Pursuit)

Путь — ломаная. На каждом кадре:

1. Если до конца текущего сегмента ближе `WAYPOINT_RADIUS_MM` — индекс сегмента += 1 (назад не ходим).
2. Ищем пересечение окружности радиуса `LOOKAHEAD_MM` с отрезками впереди. Берём пересечение **дальше по пути**.
3. Нет пересечения → цель = конец текущего сегмента (робот догоняет путь).
4. Желаемый курс = `atan2(ty − y, tx − x)`.

Финиш: расстояние до **последней** точки ≤ `GOAL_TOLERANCE_MM`.

У финиша `cruise_speed` линейно снижает `BASE_SPEED`, пол не ниже 25%, чтобы не проскочить допуск.

Это учебный Pure Pursuit, не полная «оптимальная траектория». Острые петли и развороты на 180° он проходит, но заложите геометрический запас на поле.

### 6.4. Почему цикл 10 мс

```python
await runloop.sleep_ms(10)
```

100 Гц достаточно для FLL-базы и не душит хаб. `dt` для PID берётся как `LOOP_MS / 1000`. Если поставите 50 мс, Kd станет другим: перенастройте. Не ставьте 1 мс: runloop и IMU столько не вытягивают стабильно.

## 7. Типичные поломки и как их чинить

| Симптом | Вероятная причина | Что делать |
| --- | --- | --- |
| Play, и сразу стоп | `PATH` из одной точки или финиш уже в допуске | Минимум 2 точки, первая (0,0), вторая дальше 40 мм |
| Едет назад | Знаки моторов | Инвертировать оба `*_SIGN` |
| Крутится на месте | Один знак неверный / перепутаны порты L/R | Шаг 4 запуска |
| Прямая превращается в усиливающуюся дугу | `GYRO_SIGN` | Поставить −1 |
| Проезжает не ту длину | `WHEEL_DIAMETER` | Метод выбега |
| Виляет на прямой | Kp или Kd велики | Этап A/B PID |
| Срезает все углы | Большой lookahead | Уменьшить `LOOKAHEAD_MM` |
| Хаб пишет ошибку порта | Мотор не в том порту / выпал кабель | Совпадение буквы и константы |
| После удара об модель едет «пьяный» | Накопленный I | Меньше Ki / `PID_I_LIMIT`, на старте миссии можно звать `pid.reset()` |
| Координаты плывут только по Y | Хаб наклонён, неверный `YAW_FACE` | Поставить хаб ровно, сменить грань |
| Программа зависает, моторы воют | Удалили `await runloop.sleep_ms` | Вернуть |

Отладка без компьютера: временно уменьшите `PATH` до одной прямой. Не отлаживайте сразу восьмёрку.

## 9. Справочник API SPIKE App 3.x

То, чем реально пользуется `main.py`.

### Импорты

```python
import math
import motor
import runloop
from hub import motion_sensor, port
```

### Гироскоп

| Вызов | Смысл |
| --- | --- |
| `motion_sensor.tilt_angles()` | Кортеж `(yaw, pitch, roll)` в **дециградусах** |
| `tilt_angles()[0] * 0.1` | Yaw в градусах. Плюс = против часовой |
| `motion_sensor.reset_yaw(0)` | Текущий курс считать нулём |
| `motion_sensor.set_yaw_face(motion_sensor.TOP)` | Какая грань хаба «верх» для yaw |

Диапазон yaw примерно −179.5° … +180°. Всегда прогоняйте через `wrap_deg`.

### Моторы

| Вызов | Смысл |
| --- | --- |
| `motor.relative_position(port.C)` | Накопленные градусы энкодера ведущего |
| `motor.reset_relative_position(port.C, 0)` | Обнулить энкодер |
| `motor.run(port.C, velocity)` | Крутить со скоростью, град/с, пока не дадут новую команду |
| `motor.stop(port.C)` | Стоп |

Плюс `relative_position` — по часовой, если смотреть на мотор спереди (документация LEGO). Поэтому на базе и нужен `MOTOR_SIGN`.

### Runloop

| Вызов | Смысл |
| --- | --- |
| `async def main():` | Точка, где живут `await` |
| `await runloop.sleep_ms(10)` | Отдать управление хабу на 10 мс |
| `runloop.run(main())` | Старт программы |

Без этой тройки Python в App 3.x не является «просто скриптом»: это кооперативная прошивка хаба.

## Быстрый чеклист перед заездом

1. База на **C+E**, цвет **A+D**, навесы **B+F**. Знаки ведущих проверены короткой прямой.
2. `GYRO_SIGN` не зеркалит.
3. `WHEEL_DIAMETER` измерен выбегом на том же покрытии.
4. Хаб ровно, `YAW_FACE` совпадает с установкой.
5. Робот стоит на (0, 0), нос по +X, не держать в руках в момент Play.
6. В `PATH` миллиметры, не сантиметры.
7. После правки кода в App вставлен **весь** файл, внизу один `runloop.run(main())`.
